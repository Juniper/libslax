libxi -- XML Input Library
==========================

Overview
--------

libxi is a fast, memory-efficient XML processing library built on top of
parrotdb's paged memory-mapped storage.  Its name mirrors its sibling
project libxo (XML output): where libxo emits structured data, libxi
ingests it.

The library has three broad goals:

* Parse XML faster than libxml2 by leaning heavily on ``memchr`` to skip
  between ``<`` and ``>`` delimiters, achieving roughly 0.5 GB/s of
  tokenized XML on modest hardware.

* Store parsed documents in a compact "tiny tree" representation that uses
  roughly 32 bytes per node versus ~200 bytes for a libxml2 node.

* Support rule-driven, streaming transformation of XML during parsing so
  that large documents can be filtered, re-tagged, or discarded without
  ever materialising the parts that are not needed.

libxi depends on parrotdb for all persistent storage.  It does not depend
on libxml2 or libxslt.


Dependency: ParrotDB
--------------------

Every persistent data structure in libxi lives inside a parrotdb
memory-mapped segment (``pa_mmap_t``).  Understanding the parrotdb
primitives is essential for reading the libxi source.

``pa_mmap_t``
    The base allocator.  Hands out 8 kB chunks backed by ``mmap(2)``,
    addressable by a 32-bit chunk number.  Supports persistence and sharing
    across processes.  Maximum segment size is 32 TB.

``pa_fixed_t``
    A paged array of fixed-size records, similar to a software page table.
    A 32-bit *atom* encodes a page number in the high bits and an index
    within that page in the low bits (the split controlled by a ``shift``
    parameter).  Supports up to 4G records of each type.
    ``pa_fixed_element`` forces a page to be allocated if not yet mapped,
    while ``pa_fixed_atom_addr`` returns NULL for an unmapped page.

``pa_arb_t``
    Arbitrary-sized allocation using a power-of-two allocator; used for
    text content that varies in length.

``pa_istr_t`` / ``pa_pat_t``
    Immutable interned strings indexed by a patricia tree.  Once a string
    is stored it cannot be freed individually, but every distinct string
    gets a unique atom number, making equality comparison a single integer
    compare.

``pa_bitmap_t``
    Paged bitmaps used by the rulebook to record which element names a rule
    applies to.

**Typed atoms.**  Raw ``pa_atom_t`` values (``uint32_t``) are wrapped in
single-field structs so the compiler enforces that, for example, a node
atom cannot be accidentally passed where a rule-state atom is expected.
The ``gen/`` subdirectory holds headers generated by ``bin/gen-code.sh``
that emit typed ``alloc``, ``free``, ``addr``, and ``element`` inline
functions for each atom type (e.g. ``xi_node_alloc``, ``xi_rstate_element``).


Source Components
-----------------

xi_source_t -- Tokeniser
~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xisource.h``, ``xisource.c``

``xi_source_t`` is a pull tokeniser that reads an XML file (or
memory buffer) and presents one token at a time to the caller.  It does
**not** build a tree; it just classifies byte ranges of the input.

The central API is::

    xi_node_type_t xi_source_next_token(xi_source_t *srcp,
                                        char **datap, char **restp);

The return value is one of the ``XI_TYPE_*`` constants defined in
``xicommon.h``:

.. list-table::
   :header-rows: 1
   :widths: 20 60

   * - Token type
     - Meaning
   * - ``XI_TYPE_OPEN``
     - Opening element tag; ``*datap`` is the tag name, ``*restp`` is the
       unparsed attribute string.
   * - ``XI_TYPE_CLOSE``
     - Closing tag; ``*datap`` is the tag name.
   * - ``XI_TYPE_EMPTY``
     - Self-closing tag (``<foo/>``); same fields as OPEN.
   * - ``XI_TYPE_TEXT``
     - Text content; ``*datap`` points to the start, ``*restp`` to the end
       (NUL termination is not always possible here).
   * - ``XI_TYPE_UNESC``
     - Unescaped text (from a ``<![CDATA[...]]>`` section).
   * - ``XI_TYPE_COMMENT``
     - XML comment.
   * - ``XI_TYPE_PI``
     - Processing instruction.
   * - ``XI_TYPE_ATSTR``
     - Attribute string (raw, unparsed).
   * - ``XI_TYPE_ATTRIB``
     - A single parsed attribute name/value pair.
   * - ``XI_TYPE_EOF``
     - End of input.

The tokeniser works by repeatedly calling ``memchr`` for the next ``<`` or
``>`` boundary rather than scanning byte-by-byte, which is the primary
source of its speed advantage.

Flags on ``xi_source_t`` (``XPSF_*``) control behaviour such as whitespace
trimming, ignoring comments, tracking line numbers, and whether the file
is memory-mapped or read into a heap buffer.

xi_workspace_t -- Storage Pools
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xiworkspace.h``, ``xiworkspace.c``

A workspace owns the parrotdb tables that back a document (or a group of
documents that share names).  Multiple trees can share a single workspace.

.. list-table::
   :header-rows: 1
   :widths: 25 55

   * - Field
     - Purpose
   * - ``xw_mmap``
     - Underlying ``pa_mmap_t`` segment.
   * - ``xw_nodes``
     - ``pa_fixed_t`` of ``xi_node_t`` records (the tree nodes).
   * - ``xw_names`` / ``xw_names_index``
     - Interned element and attribute names (``pa_istr_t`` + ``pa_pat_t``).
       Two nodes with the same name atom are guaranteed to have identical
       names; comparison is O(1).
   * - ``xw_ns_map`` / ``xw_ns_map_index``
     - Pool of ``xi_ns_map_t`` records mapping namespace prefixes to URIs.
       Namespace handling collapses identical prefix→URI pairs to a single
       atom.
   * - ``xw_textpool``
     - ``pa_arb_t`` for variable-length text content and attribute values.
   * - ``xw_nodeset_chunks`` / ``xw_nodeset_info``
     - Storage for node sets (see below).

xi_node_t and xi_tree_t -- The Tiny Tree
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xinode.h``, ``xitree.h``, ``xitree.c``

The tree representation follows the *tiny tree* pattern: each node carries
only two child-related pointers, keeping the node footprint at 32 bytes.

``xi_node_t`` fields:

.. list-table::
   :header-rows: 1
   :widths: 20 60

   * - Field
     - Meaning
   * - ``xn_type``
     - Node type (``XI_TYPE_*``).
   * - ``xn_depth``
     - Depth in the hierarchy (origin 1; 0 reserved for the virtual root).
   * - ``xn_flags``
     - Attribute presence and extraction flags.
   * - ``xn_ns_map``
     - Raw atom for the namespace prefix→URI mapping for this node.
   * - ``xn_name``
     - Raw atom for the element/attribute name in the workspace name pool.
   * - ``xn_parent``
     - Atom of the parent node.
   * - ``xn_next``
     - Atom of the next sibling, **or** the parent if this node is the last
       sibling.  The depth field distinguishes these two cases during tree
       traversal.
   * - ``xn_contents``
     - Overloaded field: first-child atom for element nodes; text atom for
       text/attribute nodes; namespace-map atom for NS nodes.

The "last sibling points to parent" trick eliminates a separate parent
pointer from every node.  Tree traversal uses depth comparisons to tell
whether ``xn_next`` is a sibling or a parent link.

``xi_tree_t`` wraps a ``xi_tree_info_t`` (which lives in the mmap and holds
the root node atom and maximum depth) together with a pointer to its
workspace.

**Insertion stack.**  The ``xi_insert_t`` structure maintains a depth-indexed
stack of ``xi_istack_t`` frames, one per level of the open hierarchy.  Each
frame records the current node atom and pointer, the last child appended
(for O(1) sibling append), the active rule action, the current rulebook
state, and the original element name (used when a rule renames a tag via
``use-tag``).

xi_parse_t -- The Parser
~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xiparse.h``, ``xiparse.c``

``xi_parse_t`` ties together a source, a rulebook, and an insertion point.
Calling ``xi_parse(parsep)`` drives the tokeniser loop: for each token it
consults the rulebook, executes the resulting action, and either inserts a
node into the tree or discards it.

The parser exposes two output mechanisms:

* **Tree building** (default): nodes are inserted into the ``xi_insert_t``
  tree via ``xi_insert_open`` / ``xi_insert_node`` / ``xi_insert_close``.
* **Emit callback**: ``xi_parse_emit(parsep, func, opaque)`` walks the
  completed tree and calls ``func`` for each node, useful for streaming
  results to a downstream consumer without holding the whole tree.

The parser also holds a **default rule** (``xp_default_rule``) used when no
rulebook is present or when the rulebook has no matching rule and no
per-state default.  Out of the box this rule saves everything
(``XIA_SAVE``).

``xi_parse_set_default_rule`` lets the caller change the parser-level
default (e.g. to ``XIA_DISCARD`` for a "discard unless explicitly saved"
policy that complements state-specific rules).

xi_rulebook_t -- Rule-Driven Transformation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xirules.h``, ``xirules.c``

A *rulebook* is a compiled set of states and rules that controls how
incoming elements are handled during parsing.  Rulebooks live in their own
``pa_mmap_t`` segment so they can be compiled once and memory-mapped into
multiple parser processes.

**States** (``xi_rstate_t``)
    A state is a named set of rules active while the parser is at a certain
    depth or context.  Each state has:

    * ``xrbs_first_rule`` -- head of the singly-linked list of explicit rules.
    * ``xrbs_default_rule`` -- fallback rule applied to any element not matched
      by an explicit rule.  If null the parser-level default applies.

    The initial state (``XI_STATE_INITIAL``, id 1) is entered at parse start.
    States are direct-indexed by their integer id, so ``xi_rstate_element``
    (which forces page allocation) must be used rather than
    ``xi_rstate_addr`` (which returns NULL for unmapped pages) when a script
    uses non-sequential state ids.

**Rules** (``xi_rule_t``)
    Each rule carries:

    * ``xr_bitmap`` -- a ``pa_bitmap_t`` recording which element name atoms
      this rule matches.  ``XRF_MATCH_ALL`` makes it a wildcard.
    * ``xr_action`` -- what to do when the rule fires (see below).
    * ``xr_use_tag`` -- optional replacement name atom; if set, the inserted
      node gets this name instead of the original element name.
    * ``xr_new_state`` -- if non-null, the parser switches to this state for
      the matched element's children.
    * ``xr_next`` -- next rule in the state's list.

**Actions** (``xi_action_type_t``, ``XIA_*``)

.. list-table::
   :header-rows: 1
   :widths: 20 60

   * - Action
     - Behaviour
   * - ``XIA_NONE``
     - No action; effectively a no-op placeholder.
   * - ``XIA_SAVE``
     - Insert the element (and its subtree) into the output tree.
   * - ``XIA_SAVE_ATSTR``
     - Save the element and preserve the raw unparsed attribute string.
   * - ``XIA_SAVE_ATTRIB``
     - Save the element with fully parsed name/value attribute nodes.
   * - ``XIA_EMIT``
     - Insert the element; equivalent to SAVE but semantically marks nodes
       intended for direct output rather than intermediate storage.
   * - ``XIA_DISCARD``
     - Push a *phantom frame* onto the insertion stack (no node allocated).
       All children, including nested elements, are silently dropped.  On the
       matching close tag the phantom frame is popped and parsing resumes
       normally.
   * - ``XIA_RETURN``
     - Force ``xi_parse()`` to return to the caller, enabling incremental or
       co-routine-style parsing.

**Rule matching.**  ``xi_rulebook_find`` walks the explicit rule list for the
current state, testing each rule's bitmap against the incoming element's name
atom.  On a miss it falls back to the state's ``xrbs_default_rule`` before
returning NULL (which causes the parser-level default to apply).

**Rulebook scripts.**  A rulebook is loaded from an XML script file.  The
format mirrors the internal data model directly::

    <script>
      <state id="1" action="save">
        <rule tag="one" action="emit"/>
        <rule tag="two" action="emit" new-state="2" use-tag="content"/>
        <rule tag="three" action="discard"/>
      </state>
      <state id="2" action="discard">
        <rule tag="name" action="emit"/>
        <rule tag="protocol" action="emit"/>
      </state>
    </script>

The ``action`` attribute on ``<state>`` sets the state's default rule.  The
``action`` attribute on ``<rule>`` sets the per-tag action.  ``new-state``
causes child elements to be matched against the named state.  ``use-tag``
renames the emitted element.

``xi_rulebook_setup`` parses a script file using a parser instance (the
rulebook compiler is itself built on libxi) and populates the rulebook's
``pa_mmap_t`` with the resulting state and rule arrays.

xi_nodeset_t -- Node Sets
~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xinodeset.h``

A node set is an ordered collection of node atom references, implemented as
a singly-linked list of fixed-size *chunks*.  Each chunk is a page of
``pa_atom_t`` values (default 256 per chunk, configurable).  An
``xi_nodeset_info_t`` record in the mmap holds the head and tail of the
chunk chain; a heap-side ``xi_nodeset_t`` wraps it with a workspace pointer.

Node sets support four semantic types (``XI_NSTYPE_*``): normal, result-tree
fragment (RTF), normal variable, and mutable variable -- mirroring XSLT
concepts for future use in the XSLT replacement.

xi_xpath_t -- XPath (Early Stage)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xixpath.h``, ``xixpath.c``

The XPath subsystem is in an early design phase.  The header defines the
outline of a compiled XPath expression as a tree of ``xi_xpath_op_t`` nodes
(operations: name-test, node-type test, predicate, OR, AND, NOT) and an
evaluation context (``xi_xpath_context_t``) and result type
(``xi_xpath_result_t``).  No evaluation engine exists yet.

xiwhiffle -- Tree Traversal
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

*Files:* ``xiwhiffle.h``, ``xiwhiffle.c``

``xi_whiffle_test`` is a utility that exercises tree traversal ("whiffling"
through the tree in the sense of scanning forward through siblings and
descending into children).  It serves as a performance and correctness harness
for the tiny-tree layout.


Parsing Flow
------------

The following sequence describes a typical parse with a rulebook::

    xi_workspace_t *xwp = xi_workspace_open(pmap, "doc");
    xi_rulebook_t  *xrb = xi_rulebook_open("script.xi");

    xi_parse_t *parsep = xi_parse_open(pmap, xwp, "doc",
                                       "input.xml", XPSF_IGNORE_WS);
    xi_parse_set_rulebook(parsep, xrb);

    xi_parse(parsep);           /* drives the tokeniser loop */

    xi_parse_emit_xml(parsep, stdout);  /* write the result */

    xi_parse_destroy(parsep);
    xi_rulebook_close(xrb);

Inside ``xi_parse``:

1. ``xi_source_next_token`` returns the next token type and data pointers.
2. For ``XI_TYPE_OPEN`` / ``XI_TYPE_EMPTY``, the element name is interned in
   the workspace name pool and ``xi_rulebook_find`` is called with the
   current stack-top state to locate a matching rule.
3. The rule action is dispatched:

   * ``XIA_SAVE`` / ``XIA_EMIT``: ``xi_insert_open`` allocates a new
     ``xi_node_t``, links it as a child of the current frame, and pushes a
     new frame.  If the rule specifies ``xr_new_state``, the new frame's
     ``xs_statep`` is set to the target state so child lookups use it.
   * ``XIA_DISCARD``: a phantom frame (``xs_node == NULL``,
     ``xs_action == XIA_DISCARD``) is pushed.  Subsequent calls to
     ``xi_insert_open`` and ``xi_insert_node`` detect this frame and return
     immediately without allocating.  Child elements inside a discard frame
     push additional phantom frames so that arbitrary nesting is handled
     correctly.
4. For ``XI_TYPE_TEXT``, ``xi_insert_node`` allocates a text node in the
   text pool unless the current frame is a phantom discard frame.
5. For ``XI_TYPE_CLOSE``, ``xi_insert_close`` pops the current frame.  If
   the frame is a phantom discard frame it is simply discarded; otherwise the
   parent frame's last-child hint is updated for O(1) sibling appends.

Code Generation
---------------

The ``gen/`` directory (produced by ``bin/gen-code.sh``) contains inline
function sets for each typed atom kind used in libxi:

* ``xi_rule_id_gen.h`` / ``xi_rstate_id_gen.h`` -- atom type declarations
  (wrapping ``pa_fixed_atom_t``).
* ``xi_rule_id_funcs_gen.h`` / ``xi_rstate_id_funcs_gen.h`` -- typed
  ``alloc``, ``free``, ``addr``, and ``element`` functions for rules and
  states inside a ``xi_rulebook_t``.
* ``xi_node_gen.h`` / ``xi_ns_map_gen.h`` -- same for nodes and namespace
  map entries inside a ``xi_workspace_t``.
* ``xi_nodeset_chunk_gen.h`` / ``xi_nodeset_info_gen.h`` -- for node set
  chunks and info records.

The ``element`` variant (e.g. ``xi_rstate_element``) calls
``pa_fixed_element``, which allocates the underlying page if it has not yet
been mapped.  This is required for direct-indexed access patterns (such as
rulebook state lookup by id) where pages may not have been allocated in
sequential order.
